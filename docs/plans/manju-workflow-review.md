# 漫剧老李流程对照与影策优化清单

状态：调研建议，未实施本清单。核查日期：2026-10-15。

## 结论

建议保留影策现有八阶段、画布节点、后台 Agent、模型渠道、计费和剪辑器，吸收外部仓库的制作规则、阶段交付标准和连续性检查方法。不要整体导入全部技能，也不要新增一套项目状态、执行队列或用户必须逐一确认的流程。

对方从来源、故事开发、资产设计、场面调度、分镜、模型提示词到质检的顺序基本合理；优势在前期制作的专业细化。它明确以提示词、素材映射说明、文稿和看板为主要交付，不能把这条流程直接等同于实际图片、视频、配音和成片的自动生产系统。[R1]

影策当前已有真实资源、异步任务、来源版本、分镜检查点、镜头映射、时间线与导出能力。更有价值的工作是统一这些能力之间的数据合同，补足制作质量检查，而不是按外部仓库的文档数量继续增加画布步骤。[C1-C9]

## 完整流程对照

| 制作环节 | 对方的长处 | 影策现状与判断 |
| --- | --- | --- |
| 选题与来源 | 区分原创、改编、对标及语言/内容类型 | 保留现有选题入口；增加可选来源及制作形式，继承到后续，不设每次重复确认的强制锁 |
| 制作方案与集纲 | 角色目标、关系、世界规则、分集任务和审稿拆得细 | 当前已有选题、方案、集纲、正文；将角色弧光、伏笔回收和事实依据补入现有结构，不恢复单独粗纲步骤 |
| 资产 | 三类主资产、声音描述、状态与参考职责 | 当前已覆盖规范、人物、场景、道具、特殊资产及生图；重点补基准/变体/实际引用的传递，不重做分类 |
| 分镜 | 文戏、动作戏按需选择规则；明确调度、节奏和连续性 | 当前逐场 Agent 已有执行骨架；补可计算状态、台词对应、节拍目的，减少只有自由文本的约束 |
| 模型输入 | 将创作稿转成可执行的模型输入，并检查素材映射 | 影策已有渠道能力和参考映射；应把分镜后的提示词阶段接入同一镜头数据与检查点 |
| 配音与视频 | 声音分层、镜头衔接和模型格式文档 | 不照搬模型名或固定参数；复用现有音视频任务，把流程文稿中的执行意图接到实际任务 |
| 剪辑与质检 | 连续性清单、问题分类和责任阶段明确 | 项目已经有入轨、渲染和交付校验；改善画布任务、镜头采用版本与剪辑结果之间的回写 |
| 导出交付 | 看板、字幕、时间线清单等便携交付 | 复用现有编辑器与资源存储；外部平台使用者再按需提供导出包，避免再建一个主看板 |

注意：`production: true` 的部分画布步骤目前生成的是制作文稿或执行清单，不能仅凭这个标志判定实际配音、视频或 MP4 已完成。与此同时，系统其他模块确有实际执行能力，不能把“画布链路未完全贯通”写成“整个系统没有”。[C1、C4、C6-C8]

## 不适合直接照搬的部分

1. **每项参数都要用户重新确认。** 对方的六道前置锁及画风确认适用于它的交互约定，与本项目已明确的简化操作、继承参数、后台执行偏好不符。影策应自动继承既有值，仅在真实缺失、矛盾或必要决策时询问。[R1]
2. **把专业经验变成一律阻断的规则。** 固定情绪曲线、镜头比例、每场必须有特定胜负结构等只能作为适用题材的建议。规则应按硬错误、条件规则、质量建议分级；对方自己也在治理此类误用。[R2、R5]
3. **直接信任模型专用数值。** 文档中的时长、参考数量、画幅及首尾帧规则，应逐一对照实际供应商接口和系统配置。创作方法、模型能力、HTTP 协议必须分层，不能用一个厂家名称统管三者。[R1、C9]
4. **把整套文档加入每次模型请求。** 按任务加载规则的思路值得吸收，但 `slice_context.py` 实际主要取文件头部固定行数和后续标题，不能据此证明关键条款已经完整装载。应按有稳定 ID 的规则块加载，并验证所需字段，而不是按文件前几十行裁切。[R7]
5. **直接移植提示词编译脚本。** `compile_project_to_feed` 在每段循环内遍历全局 `characters` 和 `props`，未按该段出场集合筛选；人物状态也从全局状态集合拼接。源码还在输出画幅后固定附加“横屏”。前者有重复上下文和错误状态应用风险，后者会与竖屏参数冲突。这是静态源码发现，未声称实际运行复现。[R6]
6. **把台词比对脚本当完整性证明。** `script_feed_diff.py` 默认使用固定示例角色名，且将投喂台词拼接后做字符片段覆盖。解析不到上游对白时没有单独失败分支；仅靠覆盖率也无法严格证明说话人、顺序、重复次数正确。应采用项目角色和稳定对白 ID，补零解析、重复、错人及乱序测试。[R8]
7. **把所有图都改成强制宫格。** 场景多角度图和故事板有价值，但现有资产板布局应保留。多格图可以辅助审阅和空间理解，是否作为模型参考取决于其能力；单镜头首帧不应静默替换为整张多格板。[R3、R9、C5]
8. **拿检查脚本成功代替制作完成。** 指纹、字段存在和引用覆盖都是必要证据的一部分，不能证明画面质量、对白表演或真正导出成功。[R5、R10]

## 推荐交付顺序

1. **第一批：01、02、06。** 先让分镜结构、对白覆盖和阶段完成证据一致，产物能可靠交给下游。
2. **第二批：03、04、05，并补 07 的最小规则分级。** 解决连续性、参考素材和后续长任务重复输入。直接复用本轮逐场检查点，避免另起队列。
3. **第三批：08、09、10、11、12。** 增强故事/表演质量，连通实际配音、视频、预演、剪辑与交付。
4. **后续：按实际项目选择 13、14；15 的回归样例从第一批开始积累。** 对外导出包根据外部工具使用需求安排。

这些工作以现有节点详情、阶段容器和项目镜头为入口。检查表、状态变化和规则命中属于内部记录，不把每条检查另做一个画布节点。硬错误优先自动修复当前单元；无法自动确定的矛盾才提问。正常计费继续统计，修复不能通过禁用计费、隐藏失败或重复重提任务来完成。

## 建议保留的用户流程

```text
选题 → 制作方案 → 分集集纲 → 分集正文
     → 规范与资产提取/参考图
     → 逐场分镜 → 镜头素材绑定与模型输入
     → 配音/视频 → 剪辑 → 质检 → 导出
```

这是现有八阶段内部的执行关系，不是新增一套导航。规则路由、覆盖检查、连续性核对、模型编译和局部返修由后台完成。允许前期在没有图片时继续文字规划；真正调用需要参考图的模型时再验证实际资源，不把不存在的占位编号当图片提交。

## 验证边界

本清单没有声称外部项目已经验证了普适的制作质量、特定模型能力或完成时间。当前系统能力依据源码与上一轮实际测试范围；本次没有重新跑完整业务验收。正式实施时，先用一集真实项目做基准，再验证上述改动是否减少输入、等待和返工，同时保留对白、剧情和连续性质量。
