# 任务缓存与队列稳定性

## 分镜工具参数与纠错记录

分镜规划和详情输入在内部持久结构解码前，按当前公开工具契约检查规范外字段，错误返回安全的位置（如 `parameters.scenes[0]`），不回显模型任意字段名或字段值。场次内部 `complete/shots/layout` 等检查点字段不能混入规划入参。此检查仅约束允许写入的字段，不代替正文覆盖、时长、资产版本与依赖等业务校验；异常对象整次拒绝，不能通过删除未知字段接受遗漏剧情的规划。

参数错误沿用现有工具纠正链路，回传当前规范并要求完整重新提交。执行记录读取服务端 `retry`，用任务与纠正组标识关联失败尝试和恢复回执，区别自动纠正与终止失败。参数变化后旧组显示由后续纠正接替，继续任务清空旧纠正状态时将旧记录收为中性历史；实际停止保留未完成原因，不把历史纠正显示为仍在运行。未更改并发配置、任务扣费或已完成镜头。

## 镜头图片的连续性依赖

画布镜头帧容器按 `pipelineId + episodeNumber` 归属，原分镜版本 ID 仍保留在每张图片上。创建和加载走同一容器归并函数，只合并能从容器、源分镜与子节点确定同集归属的未锁定容器；重挂子节点并重定向连接，保留图片和任务 ID。新容器使用稳定 ID；历史图片不跨分镜版本自动复用。没有修改数据库格式或历史任务输入。

首帧先采用当前镜头的资产外观参考；尾帧、关键帧在原参考集合中加入本镜已生成首帧，并明确各参考图的角色。连续镜头共享相邻端点，因此一串 N 个连续镜头使用 N+1 张边界图片，按实际图像依赖推进。独立场次可以并发，关键帧在首帧完成后也可以并发，所有名额继续来自全局策略。不能为填满并发窗口而跳过首帧依赖；失败、暂停或来源变化显示具体等待原因。未完成的前镜详情不创建独立替代首帧。

实际提交图片任务时，节点保存 `storyboardFrame.continuityReference`，包含所用首帧节点及媒体签名；优先使用持久资源键，不因临时预览 URL 更新而失效。替换首帧后不再把依赖旧图的衍生结果视为当前结果，显式再生成保留旧图，下一次实际调用重新核对当前版本。提示词区分不变项与目标时刻变化项；明确换装/换场仅覆盖相应状态。引用图片数仍受模型能力检查，不静默丢弃资产参考，也不修改扣费或自动重做历史成功图。

参考开源资料：[StoryDiffusion](https://github.com/HVision-NKU/StoryDiffusion) 的跨画面一致性建模、[IP-Adapter](https://github.com/tencent-ailab/IP-Adapter) 的图像与文本联合条件，以及 [Replicate prompt-images skill](https://github.com/replicate/skills/blob/main/skills/prompt-images/SKILL.md) 的角色参考和定向修改建议。本项目借鉴参考图锚定与仅修改明确变化项的设计，没有接入这些项目的自注意力模块、适配器权重或模型训练，也不据此承诺第三方生图模型绝对一致。

## 分镜按集并发与集内批量补全

当前检查点为 `storyboard-episode-v3`。并发单位是集，每集只保留一个持久执行通道；不同集的模型调用共同读取全局 `agentConcurrency`。流程为制作简报、场次规划、全部镜头轻量清单与占位、按场顺序批量补全、整集审查。集内每批提交 1–8 个连续缺失镜头，不再为每镜创建子任务；一次提交全部校验成功后原子保存，不接受部分有效批次。

补全只携带本批对应正文、简报、空间约定、实际前镜、后镜规划及显式前置结果，不读取全量资产库。整集审查直接取得本集完整正文与完整镜头，避免只看截断摘要后反复逐场读取。每场时长预算必须全部可分解为设定的单镜范围，不再允许每场各留一个短尾；整集与单镜范围无合法组合时在调用前明确报错，不通过修改秒数或删剧情凑时长。

进度通过 `executionMode=episode` 与 `episodeTaskStatus` 展示当前集调用的真实队列状态，`currentItem` 表示当前批次范围，`concurrencyLimit` 仍是全局上限。暂停停止后续调度，已有付费响应允许结算。进程恢复按规划编号补缺，不覆盖手改提示词、视频或帧图。旧版在途子响应先结算再切换，无新增逐镜派发；历史计费与事件回执保留。用户要求整集重做时创建新版本，旧稿保留供核对，不自动重做已完成版本。

整集语义审查可要求调整合法但不符合剧情时间关系的场次预算。返修清空指定场次的布局并保留旧稿，此时检查点返回 `canRebudget` 和预算调整指引；模型可先调用 `production_storyboard_plan` 保存完整新预算，再重新布局。仅调整已指定返修场次，保持场次 ID、正文范围和未返修的已完成场次预算；不能因为原预算数学上合法就直接复用旧预算，也不能让布局入口阻断预算调整。

### 历史逐镜调度回执

并发子任务完成后会精简 `input_json`，因此结果结算必须从持久化制作作业的 manifest 判断工具：分镜使用 `production_storyboard_expand`，制作方案使用 `production_submit`，不能从已精简请求推断工具。仍校验单一工具调用、镜头编号、场次、前置依赖和来源版本，不能通过放宽校验接收错误结果。历史误判仍保留成功回执的镜头允许重新校验保存，恢复时沿用原调用，不因此新增模型任务；已丢失当前回执的项按正常继续/重试处理，不猜测跨版本旧结果。

`run.production.parallelItems` 返回各项 `key/name/taskId/status`，通过一次仅查询任务 ID 与状态的用户隔离查询组装，不读取模型正文，也不为每次状态变化保存整张画布。列表、节点详情与容器会话区分执行、排队、响应完成待保存、重试与失败；`concurrencyLimit` 始终表示所有任务共同遵循的全局 Agent 上限，每集在途回执数不代表本集实际占用线程数。状态读取失败显示核对中，不虚报正在执行。

分镜检查点使用 `storyboard-layout-v2`：先完成本集制作约束简报与场次预算，再由 `production_storyboard_layout` 一次保存所有未完成场次的轻量镜头清单。清单确定总数、稳定编号、原文段范围、时长、剧情目标、入出状态与构图基准，立即写入原分集分镜列表占位；不另外创建节点。清单必须覆盖原文并符合单镜与整集时长，前向依赖、循环、改写已有结果或不完整清单在持久化前拒绝。

服务端复用制作方案的持久并发调度器，按系统 `agentConcurrency` 逐镜调用 `production_storyboard_expand`；不占用普通文本并发，也不新增业务固定上限。每次只传本镜对应正文、已保存简报、前后镜规划及显式依赖的实际结果，不读取全量资产库；模型返回正文已有资产编码，由现有解析器关联当前版本的资产与参考图。共同规划已经确定的端点不强制串行，确需实际前镜结果的镜头使用 `dependsOn`，前置保存后才调度。

镜头独立入队、计费、校验并保存，乱序返回仍按规划顺序排列；完成一镜即可使用其视频和画面制作入口。占位行保留 `detailStatus`、`detailTaskId`、`detailError`、`plannedGoal`、`detailDependencies`，分别表达计划、已调度、重试、失败和就绪；未完成详情禁止提交空媒体提示词。前镜未完成时后镜共享首帧继续等待，后镜尾帧和关键帧等待本镜首帧图片，不能另付费创建替代首帧破坏共享关系；独立镜头继续并行。

暂停停止新增调度并保存在途结果，恢复和进程重启沿用原子任务回执与规划编号，仅补缺失/失败镜头。来源变化或目标删除不重试计费、不写入旧结果；逐镜检查点保留已完成行的手改提示词、视频和帧图。全部详情完成后仍需整集审查通过，不能把清单生成或单镜成功当作整集完成。旧版分镜在模型调用边界升级，有效已有镜头保留，旧版在途响应先按原合同结算；无需数据库迁移。

## 正文完成度与定向扩写

正文使用本集集纲和所引用资产写作，不把集纲的 150–250 字目标套到正文。版本 4 合同可携带单集时长与语言；小请求同样经持久协调器生成初稿，大请求只精简相关参考，不摘改本集集纲。检查是启发式完成度筛查，不是实际媒体测时或艺术质量评级。

初稿满足检查时没有额外模型审查。明显缺少戏剧展开、有效节拍或时长范围不符时，使用固定 `body-expand` 子任务做一次整集定向补写；后续 Worker 唤醒读取同一子任务，不递归复检生成。补写失败或没有改善时保留初稿，失败调用仍按既有账务处理，不能通过交付初稿抹除费用。所有候选文稿保留在各自子调用中，最终文稿不混入诊断说明；残留问题通过详情 `qualityWarnings` 明示。

新任务和用户显式重试使用新合同；不升级历史在途输入，不自动重做用户已有正文。文本并发、余额检查、未知上游费用保护和用户取消语义不变。

正文时长子合同 `bodyWriting.version: 2` 按内容先写再估时，不再要求每段 5–20 秒。逐段粗筛口播过密、零时长及少量内容配长停顿；不把服装、站位、布景描述当作时间来源，不因句子少或标了 7 秒就一律判错。1–3 秒的短促反应不受原空节拍字数门槛限制。此检查仍是启发式，不能判断所有表演留白；修订提示要求保持有效反应和人物选择，不灌对白或形容词。修订候选不得用破坏整集完整度换取较少局部警告，也不因单纯更长而被优先采用。版本 1 的旧在途请求继续使用原校验和确定性修订输入，避免代码升级改变已经提交的模型调用标识。

## 按类型独立并发

后台领取任务分为图片、普通文本、Agent 模型调用、视频、音频和其他任务六条独立队列。默认执行并发分别为 6、3、3、2、3 和原 `workerConcurrency`；后台“资源与策略”可分别修改。先按类别筛选再领取最早任务，因此较早排队的图片不会挡住文本。每轮每类派发数量有界，快失败或持续新增任务也不会独占扫描。

`cloud_agent*` 与 `agent_memory_compact` 文本调用归 Agent；Agent 发起的媒体按媒体类型归类。短剧文本分批父任务及其文本子调用归普通文本，父任务等待子结果时继续释放执行租约；字幕转写归音频，时间线导出归视频。制作方案内部的独立文稿窗口直接读取 `agentConcurrency`，不再另设三项上限；前置依赖仍必须完成后才能执行后续项目。

### 统一策略来源

所有业务并发从系统“资源与策略”读取。画布批次与批量创作表的旧 `concurrency` 字段只保留数据兼容，不再影响调度；Agent 工具不再提供 `set_concurrency`。渠道旧 `concurrencyLimit` 不再覆盖系统策略，新保存和公开渠道信息中的该字段为 0。修改并发不会修改任务内容、订单或历史产物。

提高配置后，下轮调度补足窗口；降低配置后保留在途请求，等待占用回落再补位，重试也遵守新上限。恢复检查点不以旧固定并发数或新的较低上限判定数据损坏。渠道等待者每次重试领取时重新读取策略，不一直沿用最初的上限。后端策略缓存最长 2 秒，Agent 会话进程上限每 3 秒检查变化后同步；进程上限仍与模型调用并发分别管理。

浏览器通过登录响应的 `runtimeLimits.concurrency` 获取公开并发值，后续刷新沿用同一认证 API 与用户作用域。新增资源策略为 `imagePreparationConcurrency`、`resourceDownloadConcurrency`、`uploadConcurrency`、`mediaRecoveryConcurrency`，默认 4、16、4、2，分别控制图片准备、资源网络下载、资源上传和后端媒体交付。浏览器资源槽位按页面实例计数，后端生成和媒体交付使用运行时协调器；这些配置不等同于数据库连接池或数据一致性互斥锁。

### 单个分批任务内的并行

短剧文本分批任务先恢复本轮全部子任务状态，再按 `textConcurrency` 补足未完成子任务窗口（默认 3）。独立材料提取及同一轮归并均可并行；实际执行仍受账号准入、文本 Worker 和渠道上限约束。任意批次完成即可补位，不等待编号靠前的慢批次，父任务详情显示已完成、处理中或排队、待调度数量。

全部材料提取完成后才进入归并，每轮归并全部完成后才进入下一轮，最终仅输出一份文稿。归并输入始终按原材料顺序排列；子任务 ID、输入和计费协议保持不变，因此旧任务可继续复用已完成结果，不因升级重复生成或再次扣费。发现失败时停止新增调用，保存已提交兄弟任务的结果后转为待恢复。

取消总任务会通过原取消及账务链路取消其独立子任务，Worker 调用上游前再次检查父任务状态；共享事实任务仍可被其他消费者复用，不随单个消费者取消。无需新增数据库表或修改已保存任务输入。

Agent 图片审批修改参数时，准备阶段沿用调用方已持有的存储锁与事务校验账号文件容量，不再次获取同一把锁；避免审批、生成和后续画布写入一起等待。此内部准备入口不对 HTTP 开放，不跳过容量、模型规格、资源归属或计费校验，真实提交前仍重新验证。

集群租约使用 `workers:<kind>`，继续执行续租、取消、租约失效隔离及完成释放。`activeTaskLimit` 按单账号、跨项目、同类型的排队加运行任务分别统计，0 仍表示不限制入队数量；入队数量与正在执行的并发是两个不同概念。新建、普通重试、未发送重试及分批子任务共用类别判断，不修改订单预留、结算、退款和原任务身份。前端批量图片/视频队列也分别统计同类任务和未提交预留，后端是最终准入依据。

所有渠道按类别独立占槽，上限取全局 `channelConcurrency` 与该类别执行并发的较小值；后台任务和系统渠道同步代理使用相同分类，不再读取渠道独立覆盖。自定义 HTTP 中转按全局 `request.customRelayConcurrency` 执行账号级请求保护，调用方传入的历史数值不作为策略来源。不把下载/保存槽位当作模型生成并发。

本轮不新增数据库迁移。旧策略缺少分类字段时补默认值，已有其他策略保留。部署必须先停止旧 Worker 领取任务并等待其响应收尾，再切换所有实例；新旧 Worker 使用不同租约作用域，不允许混跑或直接滚动扩容。回退也先排空执行中的请求，保留排队任务和账务，旧版本将恢复原共享 Worker 口径。

## 详情读取和日志筛选边界

任务中心打开详情只读取任务和日志，不在该路径调用画布结果同步。后台同步遇到短剧领域项目任务（`domainProjectId` 等于任务 `projectId`）或没有生成节点关联时跳过画布写回，避免把短剧项目 ID 当作画布 ID 查询。

管理员请求明细列表及 CSV 导出支持 `recordType`：省略或 `request` 默认仅请求（隐藏视频轮询，并排除下载、上传、本地保存、素材登记明细）；`download` 只包含 `request_kind=download`；`all` 包含全部阶段。非法值返回参数错误，管理员权限校验保持不变；该筛选不改变统计聚合接口。

## 媒体交付恢复的资源边界

声明式协议已经返回作品地址后，先加密保存任务恢复记录，再执行下载、存储、素材登记。交付错误不进入模型路由切换，不创建新生成任务。已下载文件优先复用；资源已就绪时跳过下载和上传，只补登记。配置为 OSS 的生成结果上传失败会明确保留错误，不像普通文件上传那样自动降级到本地存储；普通上传行为不变。

- 媒体交付读取全局 `resource.mediaRecoveryConcurrency`（默认 2），通过 `resources:media-recovery` 协调租约计数及续租；Redis 部署下跨实例共享，本地 SQLite 使用进程内协调器。满载时通过原任务 `next_poll_at` 延迟领取，不重复生成或扣费。租约释放后后续恢复继续使用原结果。
- 下载流式写入数据目录的 `media-staging`，单次下载最多三分钟，文件上限取运行时生成文件限制与 512 MiB 中较小者；暂存目录逻辑占用上限为 512 MiB，先预留空间再写入。
- 成功后立即清理对应暂存文件；超过 24 小时的暂存文件在下次分配空间时清理，不为闲置服务常驻一个清理循环。暂存文件不可用时只尝试原地址，不重新生成；只有内联结果且文件丢失时明确失败。
- 多实例切换时，暂存文件只有位于共享数据卷才可直接复用；没有共享暂存文件但有有效源地址时可以重下载。数据目录和 settings-key 需要稳定保留，不能以临时容器目录代替持久化配置。
- 出站下载沿用 SSRF 防护；同源才附带渠道鉴权。恢复地址仅加密留存，下载明细隐藏路径和查询参数，错误日志不写入原始带签名的 URL。
- 自动重试有次数和时间窗口上限，手动重试也有限额。源地址过期、权限问题、配额不足等不会无限循环；不承诺已经过期且无暂存文件的作品一定可恢复。

章节提取采用独立提示词操作 `chapter_assets_extract`，受保护输出契约为 `chapter-assets/v1`，要求 `characters`、`scenes`、`props` 三个数组。场景和道具要求非空的 `name`、`description`、`prompt`；角色继续执行原角色契约校验。写入候选资产时场景映射为 `environment`，继续使用现有服务的项目归属、去重与写入校验，不新增数据库字段。

## 范围与事实源

当前任务仍由数据库持久化、API 进程内 worker 领取和执行，Redis 负责跨实例并发协调。本轮是热点读取和租约的止血修复，不是独立任务系统迁移，也不能替代线上事故取证。

- 数据库继续作为任务、额度、账务和权限的事实源。没有把任务或账本迁入 Redis，没有修改表结构或新增迁移。
- 新增缓存是每个后端实例的有界内存读缓存，不是通用 Redis 业务缓存。实例增加时，缓存容量与不同实例的回源量会随之增加。
- handler 负责 SSE 协议和登录上下文；service 负责读缓存、并发协调和执行生命周期；repository 负责有条件的租约写入与事务。

## 画布任务摘要与刷新恢复

任务列表的摘要通过 `clientContext.nodeId` 返回画布节点关联，不为恢复任务返回完整 `inputJson`、渠道配置或密钥。前端优先读取摘要中的节点 ID，任务详情仍可从输入元数据取得节点 ID；原有创作会话、章节和镜头工作流上下文继续保留。

已持久化任务 ID 的节点直接按 ID 恢复。缺少任务 ID 时，画布查询当前项目最近 100 条任务摘要并按节点 ID 匹配；这不是全量历史扫描，超过该范围的旧任务仍可能无法自动发现。任务读取继续遵循当前用户与项目的访问边界，不新增数据库字段或迁移。

## 热点读取保护

| 读路径 | 缓存 / 回源限制 | 故障行为 |
| --- | --- | --- |
| worker / 渠道全局并发策略 | 2 秒 TTL，1 条目、1 个同时回源，正文预算 1 KiB | 读取失败不使用默认高并发；暂停投递或返回明确错误 |
| 文本任务 SSE 回放 | 750 毫秒 TTL，256 条目、8 个不同 key 同时回源，正文预算 8 MiB | 同 key 合并回源；超过容量返回繁忙，不创建无界的不同 key 等待队列 |
| Redis 路由版本检查 | 250 毫秒 TTL，1 个同时回源 | 失败保留原有本地版本回退；不保证 Redis 故障时跨实例实时失效 |
| 模型路由目录 | 沿用 30 秒 TTL，刷新串行，失败冷却 2 秒，数据库回源期限 5 秒 | 首次失败明确返回错误；已有快照只能在同版本、最多 5 分钟的原有过期窗口内降级 |

读缓存按 LRU 淘汰，正文预算是估算值，不等于进程总内存上限；回源中的数据、当前请求和等待中的连接不包含在正文预算内。超大结果仅返回给当前读取者，不保留为缓存。普通失败冷却 1 秒，不返回过期成功值；请求取消和超时不缓存。回源异常退出释放容量和等待者，原始 panic 仍交给原有错误处理。

并发策略保存或重置成功后立即清除本实例缓存，其他实例在 2 秒 TTL 后重新读取。计费、配额和其他调用 `RuntimePolicy()` 的强校验路径仍直接读取数据库。

SSE 缓存 key 包含用户、任务和 `after` 游标，回源仍检查归属；返回副本避免调用者改写其他连接的增量。`GET /api/tasks/:id/text-events` 的事件格式、递增序号、`Last-Event-ID` / `?after=` 和 15 秒心跳不变。终态最多受短缓存窗口延迟；已经建立的流遇到回源失败仍发送 error 并关闭。`/text-deltas` 普通查询没有纳入此缓存。

这是合并相同游标的轮询读取，不是事件驱动推送；不同游标和不同实例仍可能分别查询数据库。连接总量、客户端重连退避及任务删除后的缓存失效仍需后续治理。

## 上游文本流

创作台 / 画布文本任务开启流式输出且模型允许流式时，声明式 `chat-completion`、`openai-response` 和 `claude-api` 协议会发送 `stream=true`，通过宿主网络层实时解析 SSE 并发布文本增量。Chat Completions 同时请求 usage 终态块；普通 JSON 响应仍由插件声明的响应映射解析。插件的请求字段、路径、鉴权以及宿主的 SSRF、取消和审计边界保持有效，未知协议不套用这些 SSE 格式。

流式传输可减少等待完整正文期间的网关超时，但不能保证上游及时发出首个数据块。收到 HTTP 524 或上下文取消时仍返回真实失败，不自动重发生成请求；计费结果不明确的订单保留待核对状态，缺少上游任务 ID 的历史请求无法靠本次修复自动找回。

## worker 与渠道槽位

- worker 全局槽位由固定 45 分钟 TTL 改为 1 分钟租约，每 15 秒与数据库任务租约一起续期；数据库任务租约仍为 45 秒。
- 每次领取生成独立 owner，不再让一个进程的所有执行共享 owner。领取数据库操作有 5 秒期限，启动策略读取有 3 秒期限。
- Redis 协调客户端关闭透明命令重试；槽位领取、续期与释放使用最多 2 秒期限。Redis 获取槽位失败时不降级成本机无限执行。
- 槽位丢失、过期或续期失败会取消该执行的 context。已经失效的槽位不能通过续期复活；释放幂等且只移除本次 token。释放失败记录日志，由租约过期回收。
- 共享 Redis 槽位键按集合内最晚的租约保留过期余量，避免短任务或新版本的短租约把旧长任务槽位提前删除。旧版本脚本本身不会获得这一保护，仍建议排空后发布。
- 渠道满载时从 200 毫秒开始指数退避，上限 2 秒，每轮在半窗口至完整窗口间随机等待，避免固定每秒五次同步争抢。空闲时仍先立即尝试领取，取消能立即结束等待。
- worker 主进度、终态、结果事务及延迟回查要求匹配 owner 且租约仍有效。过期执行者不能覆盖已被重新领取的任务；条件更新没有命中时，终态协调器不得继续退款或完成会话。

**边界**：租约不是外部供应商的幂等保障。上游请求不一定响应取消；提供商状态回调、部分进度和关联资源写入尚未全部传播 owner，不能宣称所有副作用都已 fencing。渠道等待仍发生在领取 worker 槽位之后，也没有新增全局积压上限或公平调度。其他用途的槽位未统一改为续期模型。

## 上线与回滚

1. 先保存故障时段的 Redis 内存、淘汰数量、连接数、延迟和重启记录，以及数据库慢查询、连接池等待、任务 queued/running 数量与最老等待时长。必要日志必须脱敏，不能导出密钥和完整用户正文。
2. 先在测试环境验证 Redis 与 PostgreSQL 双实例：长任务超过原租期仍只占一个槽位；停止 worker 后槽位恢复；Redis 断连时暂停领取；旧 owner 写入失败；SSE 断线续传无重复或漏终态。
3. 采用维护窗口排空旧执行者，再发布新版本。Compose 当前默认优雅退出时间由 `CANVAS_SHUTDOWN_TIMEOUT` 控制，默认 10 分钟，不足以保证最长 60 分钟渲染自然完成；发布前核对活跃任务，不能把进程退出视为任务排空成功。
4. 保留 `canvas:slots:*` 等现有 Redis key。旧进程的 45 分钟分数可能暂时占槽，应先确认旧执行者已结束并观察租约自然回收，**禁止用 FLUSHDB、批量删槽位或批量重投收费任务来解堵**。
5. 回滚不需要数据迁移，但旧版本仍有原来的固定租期和缺失写入保护。避免新旧版本混跑，不应把回滚视为稳定性问题已经解除。

本次不部署、不清理线上缓存、不修改线上任务或触发真实收费请求。仅凭代码修复和本地测试，不能认定某次线上事故根因已确认或故障已消除。

`TestRuntimeCoordinatorRedisLeasePreservesLongestTTL` 在 PATH 中存在 `redis-server` 时自动启动临时 Unix socket Redis，检查长短租约混用、容量、过期拒绝续期及幂等释放；它不读取 `REDIS_URL`，不连接部署环境。缺少二进制时明确跳过，不视为 Redis 集成已通过。
